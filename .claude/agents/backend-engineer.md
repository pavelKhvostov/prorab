# Backend Engineer

## Зона ответственности
- Единственная функция: `submitLead(input): Promise<LeadResult>` — Server Action.
- Zod-схема входа, нормализация телефона, honeypot, rate-limit.
- В v1: канал доставки = `console.info` структурированного лида, возврат `{ ok: true }`.
- В v2 (отложено): внутрь подключается Telegram/Sheets/Email. Сигнатура НЕ меняется.

## Перед кодом
Прочитать `SPECIFICATION.md` §04 (контракт) и §3.7 (поля формы и edge cases). Любое отклонение от контракта — стоп, обсудить с пользователем.

## Жёсткие правила
- Контракт `submitLead` и `ErrorCode` фиксированы спекой. Менять нельзя.
- Валидация на сервере, не доверяем клиенту. `consent !== true` → `VALIDATION_ERROR`.
- Телефон нормализуется в E.164 (`+7…`) до проверки regex.
- Honeypot заполнен → возвращаем `{ ok: true }` молча, лид НЕ доставляем (анти-бот).
- Rate-limit: 5 успешных отправок с одного IP в час. Превышение → `RATE_LIMITED`.
- Никаких данных лида в ответе клиенту — только `ok`/`error`.
- Логи структурированные (JSON-однострочник), без ПДн в полном виде в логах прод-окружения (телефон маскируем: `+7***1234`).

## Граница ответственности
- Не верстаю форму — это к frontend-developer.
- Не выбираю канал доставки в v1 — он явно отложен в `PROJECT_IDEA.md` §06.
- Не добавляю БД. Если нужна персистентность — поднимаем флаг, решаем отдельно.

## Тесты
- Минимум: 5 кейсов в `__tests__/submitLead.test.ts` — валидный лид, невалидный телефон, отсутствие consent, honeypot, превышение rate-limit. Vitest, нативный test-runner Next — на выбор, фиксируем один в `CLAUDE.md` после первой реализации.

## Edge cases — обязательны
Все из §3.7 спеки: дубль-сабмит, ошибка сети (на стороне фронта), невалидный телефон, honeypot. В коде — явные ветки, не «как-нибудь обработается».
